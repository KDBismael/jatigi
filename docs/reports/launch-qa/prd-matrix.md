# Warko PRD implementation and launch evidence

Audit date: 2026-10-30. Source: full 439-line `/Users/MACPRO/Downloads/planning_prd-warko.md`, especially sections 3–6 and acceptance stories US1–US8. Repository evidence below was inspected read-only. No database queries, customer-data reads, app changes or test execution were performed for this matrix.

**Production verdict: not ready for a successful first-use launch on the tested backend.** All five fresh QA signups returned 201, but all five onboarding attempts returned 500. Four of five personas encountered product-mutation 500s and four of five observed an empty catalogue; the mobile tester submitted a real first product once and received 500. An order could not be completed because no product was available. Code and unit/component tests exist for much of the PRD, but that does not establish deployed schema compatibility, successful persistence, access isolation or real payment/email delivery.

## Scope and evidence rules

- Authoritative current overrides replace stale PRD values: Découverte allows **100 orders/month**, warning at **95**, one driver, one owner; **live sessions in every plan**. Do not report the old 30/25 thresholds or paid-only lives as missing features. Source: `lib/billing/plans.ts:5`, `components/billing/subscription-usage.tsx:6`, migrations `20261029170008_discovery_100_orders.sql` and `20261029170009_live_sessions_all_plans.sql`.
- User explicitly selected **email-only** lifecycle communication and deferred N8 SMS/WhatsApp. N8 is deferred scope, not a launch omission. Renewal is manual hosted owner payment with email reminders, not automatic off-session charging.
- Fixed **XOF** is an intentional owner decision documented by [SaaS setup](../../saas-setup.md); multi-currency is not required. The manager role is the restricted delivery manager per user override; old PRD references to manager live access do not require expansion of that role.
- “Code present” means matching routes/services/UI and named test files exist. Tests in this table were not rerun in this audit, and their existence or previous passing status is not production E2E evidence.
- “Blocked / not proven” means the real end-to-end journey could not validate that feature on this backend. It does not mean every listed API was attempted and failed.
- Five-persona HTTP results and missing-schema/configuration inventory below were supplied by the coordinating launch audit. The mobile journey was directly observed by this author; see [mobile report](../qa-personas/mobile-before.md). No additional DB access was used to reproduce the inventory.

## Deployment prerequisites already found by launch audit

The coordinating audit reports the tested backend is behind repository migrations: missing product-variant/media structures, `billing_settings`, `billing_invoices`, `subscription_grants`, `notification_jobs`, `organizations.country` and `orders.delivery_date`. This matrix does not independently query or certify a complete schema diff. Repository migrations for many of these features are present, so the immediate distinction is **migration/configuration deployment**, not proof those features have no implementation.

See the coordinator’s non-secret [readiness output](readiness.json). The same audit reports only the three Supabase environment keys available locally; Moneriz, email provider/sender, cron and unsubscribe configuration are absent. Local absence does not prove hosted production environment absence. Conversely, a route/test file and a successful build cannot establish the hosted keys, scheduler, callback URLs, storage policies or schema are correctly deployed.

Before a production pass can be claimed, deploy/reconcile the reviewed migrations and required configuration, then rerun the real first-use journey. Validate operational features using disposable shop-owned records and separate roles; validate payments only under an explicitly authorized safe provider flow, and scheduled email delivery only under separately authorized recipient testing. Do not substitute fake API success, unit-test results or demo screenshots for those checks.

## Concrete remaining acceptance distinctions

1. E11 uses owner-created credentials rather than an emailed invitation, as evidenced above. Treat invitation semantics as a remaining literal-PRD distinction; the UI must not promise an email was sent. E8 restricted-manager permissions and E12 fixed-XOF settings follow explicit owner decisions and are covered scope, not gaps.
2. Owner-approved renewal is reminders, grace-period handling and fresh hosted owner payment. This supersedes old PRD automatic-renewal wording. Keep product promises aligned and do not invent or silently add recurrent charging.
3. The audit did not establish acquisition conversion, retention, MRR accuracy, real-time reconciliation, tenant isolation or physical-printer behavior. Those remain unvalidated; PRD ambitions and test filenames are not measured results.
